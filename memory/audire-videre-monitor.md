Gil (2026-09-20) made me the standing **monitor for audire-videre**. Rules he set: use subagents for tasks; do NOT ask him about ordinary work, only about genuinely high-risk commands; he goes AFK and wants auto mode (no prompts). Consistent with earlier limits: no sudo on audire-videre, never use the `docker` group as a root bypass, no changes to edgerunner's migration, ask before anything destructive.

**Watchdog:** `/home/sinewave/bin/audire-monitor.sh` (built + tested by a subagent, then I excluded the known-noise `drkonqi-coredump-pickup.service` alongside `magi-d555-stream.service`; backup `audire-monitor.sh.bak`). Read-only; state in `~/.cache/audire-monitor/`. It prints ONLY on transitions: `ALERT <check>`, `RECOVERED <check>` (both need 2 consecutive polls), `EVENT kernel-error|oom-kill|io-error|rebooted` (rate-limited 1 per 5 min per kind), and an hourly `STILL-BAD` reminder. Checks: failed units (system+user), disk/inodes for / /var /home /tmp /boot at 85%, mounts present and rw, memory/swap, load, temps, gateway 192.168.8.1, Ubiquiti switch .155, pings to melchior/balthazar/repositorium/edgerunner, dashboard :8090 + magi-dashboard unit, docker containers exited non-zero. `--once` prints a status line per check; `--self-test` proves the alert logic. A lock file stops a second instance.

**CUT OVER 2026-09-21 06:29 CDT: the watchdog is now a persistent systemd USER service `audire-monitor.service` (enabled, linger=yes, Restart=always), so it survives reboots and my session freezing.** Script v2 (19 checks, adds `switch_netgear` = GET http://10.0.0.26/ unauthenticated; v1 kept as `~/bin/audire-monitor.v1.sh`). It appends events to `~/.cache/audire-monitor/events.log` and writes `~/magi_dashboard/static/monitor.json` every poll (schema: generated, interval, host, uptime_s [host uptime], overall, checks[name,state,detail,since,bad_streak], events[ts,kind,check,text], newest last), served at `/static/monitor.json`; the dashboard Monitor tab (`/static/monitor.html`, `#monitor`) reads it. Manage: `systemctl --user status|restart|stop audire-monitor`, `journalctl` is NOT used (stdout goes to events.log).
**My live watch is now just a tail:** Monitor command = `tail -n0 -F ~/.cache/audire-monitor/events.log` plus a 60s heartbeat that emits `WATCHDOG-dead` if the service is inactive or monitor.json is >150s old. Timeout 1800000 max, so RE-ARM at each expiry (the service itself keeps running regardless). Do NOT run a second copy of the script by hand (lock).

**Triage rules I follow:** a peer-down alert for melchior/balthazar/repositorium/edgerunner is usually the owner powering things off; check before escalating. PushNotification only for things Gil would act on (disk near full, remounted read-only, OOM, I/O errors, repeated unit failures, reboot he didn't plan), not for routine recoveries. Baseline on 2026-09-20 was healthy; see [[magi-ups-power-down]] for the baseline numbers and known noise list.

## Lessons from the first overnight (2026-09-20 23:00 -> 2026-09-21 06:00)
- **This session freezes while Gil is idle/AFK.** The Monitor's 30-min expiry notice reached me ~5.5 h late, and two background subagents stopped making progress at 23:19 (output files stale for 6+ h, status still "running"). The HOST did not sleep (uptime continuous, no suspend entries, no journal gaps), so the watchdog PROCESS may have kept polling, but events are only delivered to me when the session is active. So the live watch is NOT reliable coverage by itself: a persistent systemd user service + the dashboard Monitor tab (in progress 2026-09-21) is the real fix. Until then, on every wake-up do a retrospective sweep of the gap (journal errors excluding known noise, OOM/IO/fs errors, failed units, disks, peers); the 2026-09-20 23:00-06:00 sweep was clean.
- **Detect a stalled subagent:** `ListAgents` says "running" but `ls -la --time-style=+%T /tmp/claude-1000/*/*/tasks/<id>.output` mtime is hours old and nothing it should have produced exists. Then `TaskStop` it and relaunch smaller (I split monitor v2 into a script agent and a dashboard agent sharing a fixed JSON schema). Never Read a subagent's .output file (huge JSONL); if you must peek, `tail -n 3` through a size-capped parser.
- Observed benign event: `peer_edgerunner` unreachable 05:27-05:31 on 2026-09-21 (3 min), self-recovered; edgerunner is flaky-ish/due for reinstall, don't escalate one-off blips.
- The Monitor tool kills the watchdog at expiry (30 min max), so the lock is released cleanly and re-arming works immediately.

## 2026-09-21 morning: persistent service proven, dashboard tab live, more lessons
- The systemd service ran straight through a second 3.5 h freeze of my session (06:47 -> 10:14): 0 restarts, status file 28 s old on wake-up, zero events. This is the payoff of the cutover: on every wake-up read `~/.cache/audire-monitor/events.log` (and `/static/monitor.json`) for the gap instead of assuming nothing happened. The Monitor tool watch is only a convenience tail now.
- **Dashboard Monitor tab is built and live** (`/static/monitor.html`, tab `#monitor`, index.html backup `index.html.bak.20260921_060543`); it shows a STALE chip if monitor.json is >90 s old. Not verified: real HTTP 404 path, the ticking counter, reduced-motion, and opening it over HTTP in a browser (tested on file:// copies).
- **Agent-liveness heuristic correction:** a stale subagent `.output` mtime does NOT prove it is dead: the dashboard agent's output sat untouched from 06:05 to 10:14 while it was alive in a long tool call (headless Chromium screenshots), and finished normally after ~4 h. The two agents I stopped earlier at 06:03 were dead-ish (no live processes, no artifacts). Better test: look for the agent's live child processes / files still changing (`find <its temp dir> -mmin -2`, `pgrep`), then decide.
- **/tmp watch:** /tmp is a tiny 436 MB LV and subagent browser tests can balloon it (headless Chromium profiles ~125 MB + a screenshot dir ~127 MB pushed it 41% -> 77% with ~35 MB/10 s spikes). Monitor alerts at 85%. Don't delete a live agent's test dirs; wait for it to finish (it cleaned up to 45%). When briefing agents that use Chromium, tell them to use `--user-data-dir` under ~/.cache, not /tmp, and to delete it.

## Recurring benign alert: peer_edgerunner blips (2026-09-21)
`peer_edgerunner` (ping to 10.0.0.137 from audire-videre) has tripped for ~1 min several times: 05:27, 06:33, 06:46 (Gil's real reboot), 12:35. At 12:35 edgerunner's uptime was continuous (5h49m, no reboot), the Netgear switch and the 10.0.0.214 router stayed up, ssh worked right after: so it is a transient on the path audire-videre -> GL-iNet NAT -> 10.0.0.x, or on edgerunner's eth0, NOT an edgerunner outage. Rule: for a lone `peer_edgerunner` ALERT that self-recovers, verify (ping + ssh uptime + switch_netgear) and do NOT push. Escalate only if it stays down >10 min, edgerunner's uptime resets unexpectedly (Gil didn't say he was rebooting it), or switch_netgear/other peers fail with it. If the noise continues, consider probing edgerunner over an additional path (its tailnet IP 100.x.x.x) before alerting.

## 2026-09-21 13:31 edgerunner reboot (investigated; benign, not pushed)
`peer_edgerunner` went down 13:32:12 and came back 13:38:09 (~6 min, longer than the usual ~60 s blips). Cause: edgerunner got a **clean commanded reboot at 13:31** (wtmp `shutdown` record present, no crash/undervoltage/mmc/EXT4 errors; `throttled=0x0`); the slow return was just a slow boot. Not attributable (Gil rebooted it earlier the same day for UPS work; likely ongoing). Facts learned: edgerunner's root has been on **NVMe (nvme0n1p2, ext4, created 2026-09-11)** all along (my "fresh NVMe = migration" guess was wrong); it is STILL 32-bit armhf Raspbian bookworm on an aarch64 kernel (so arm64 containers/UniFi arm64 remain blocked, the reinstall has NOT happened); tailscale serve config (:8090 dashboard, :8239 switch), smcroute, docker, tailscaled and sshd all came back on their own after the reboot. Its journal is volatile so a previous boot's logs are never available; check `last -x shutdown reboot` (wtmp persists) to tell clean reboots from crashes. The 12:35 blip, by contrast, had NO reboot (uptime continuous), so it was a genuine transient on the network path. Both kinds are benign; only escalate per the rule above.
