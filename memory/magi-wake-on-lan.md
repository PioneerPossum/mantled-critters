## REAL TEST RESULT (2026-09-21 17:11): FAILED
Powered off melchior (`systemctl poweroff`), confirmed down, sent 4 rounds of magic packets from audire-videre on the same LAN (`~/bin/wol_send.py <MAC>`: UDP broadcast to 192.168.8.255 and 255.255.255.255, ports 9 and 7): it did NOT wake in 200 s. So a halted Pi 5 with the USB dongle cannot be woken by LAN magic packet (USB ports/dongle aren't kept alive in halt; there is no suspend state either: /sys/power/state is empty). Melchior was left OFF and needs a physical power-cycle. I deliberately did NOT shut down balthazar or repositorium after the failed test (it would have stranded all three); Gil was asked how to proceed. edgerunner's built-in macb WoL is very unlikely to help from halt either (untested). audire-videre depends on BIOS ("Wake Up on LAN" enabled, ErP/Lowest Power State disabled) AND on cabling the ONBOARD NIC; the USB dongle won't wake it from S5.

## Other wake mechanisms
- Pi 5 RTC alarm works: all Pis have `rpi-rtc` with `/sys/class/rtc/rtc0/wakealarm` and default EEPROM (POWER_OFF_ON_HALT/WAKE_ON_GPIO unset). `echo +N | sudo tee /sys/class/rtc/rtc0/wakealarm; sudo poweroff` should wake it after N seconds, BUT there is no RTC battery (charging_voltage 0) so the alarm is lost if 5V power is removed: useful for "shut down but keep power on", useless for the UPS work where power is unplugged. (Untested.)
- For unplug/replug (UPS migration) the Pis simply auto-boot when power is applied (default), so WoL is irrelevant there.
- Real remote power control would need switched power (smart plug / UPS outlet control / PoE port cycling on the Netgear GS308EPP if a Pi were PoE-powered), not WoL.

## 2026-09-22: KVM tailnet visibility RESOLVED
Gil couldn't reach the KVM (10.0.0.144, tailnet node `glkvm`) from his Windows PC while routing through GL-E5800 as exit node. Root cause (confirmed live): GL-E5800 advertises a totally different subnet (192.168.10.0/24, a separate site), and being an exit node only carries default (0.0.0.0/0) traffic — it never gave LAN-IP-style access to 10.0.0.0/24 in the first place. His Windows PC also has NO Tailscale client of its own; all its traffic depends on GL-E5800 as gateway.
Fix, done jointly: (1) I advertised host routes from **edgerunner** (which physically sits on the 10.0.0.0/24 segment): `sudo tailscale set --advertise-routes=10.0.0.144/32,10.0.0.26/32` (scoped host routes, not the whole /24, to avoid the Xfinity-default-subnet collision risk noted elsewhere). (2) Gil approved both routes in the Tailscale admin console — confirmed live via `tailscale status --json` on edgerunner, `Self.PrimaryRoutes` now shows both `/32`s as approved+active. (3) Gil separately used a tool called **netpath** (https://github.com/PioneerPossum/netpath, unfamiliar to me, don't assume behavior without his notes) to force a direct route over the wire to his tailnet through GL-E5800 on the Windows side. (4) Confirmed working: Gil can reach the KVM now.
Gil said a memory-file dump about the netpath side of the fix is coming separately — read it when it arrives and fold in the client-side details I don't have visibility into (I have no access to his Windows PC or to GL-E5800 itself, no SSH/admin creds for either).
