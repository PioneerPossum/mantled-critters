**Live D555 → melchior camera bridge — built and verified end-to-end 2026-09-15.** melchior's `magi_detect.py` now runs Hailo inference against the D555's **live** color feed instead of the bundled sample video. Scoped to melchior only this session (balthazar intentionally untouched — separate concurrent agent work there).

- **Architecture:** audire-videre (D555, x86_64) captures color frames via `pyrealsense2` and re-encodes them as an RTP/H264 stream sent over UDP directly to melchior, which hailo_apps consumes natively.
- **Why this shape:** investigated `hailo_apps.python.core.common.core.py`'s `resolve_input_arg` first per the task brief — that function only resolves camera keywords/`/dev/video*`/local paths, no URIs. But it turns out `GStreamerDetectionApp` (via `GStreamerApp.__init__` in `core/gstreamer/gstreamer_app.py`) **never calls `resolve_input_arg` at all** — it takes `--input` literally as `self.video_source` and passes it through `get_source_type()` (in `core/gstreamer/gstreamer_helper_pipelines.py`), which has first-class `rtsp://` and `udp://` handling built into `SOURCE_PIPELINE()`. So `--input udp://:<port>` (or `rtsp://...`) just works, no custom pipeline construction or CLI patching needed. The `udp://` path builds `udpsrc port=<port> ! application/x-rtp,encoding-name=H264,payload=96 ! queue ! rtph264depay ! h264parse ! avdec_h264`.
- **Sender — audire-videre:** `/home/sinewave/magi_stream_d555.py`. No system GStreamer H264 encoder or `gst-rtsp-server` was available on this box (only `gstreamer1.0-plugins-good`/`base`/`x` installed, no `-bad`/`-ugly`, and **no passwordless sudo on audire-videre** to apt-install more — unlike melchior/balthazar, this box's sudo needs a password, so a human would need to run any `apt install` here). Worked around entirely in userspace: `pip install --user --break-system-packages av` (PyAV, ships its own static FFmpeg build including `libx264` and RTP muxing) — grabs 640x360@30fps BGR frames via `pyrealsense2`, encodes with `libx264` (`preset=ultrafast, tune=zerolatency, profile=baseline`, ~800kbps, keyframe every 2s via `x264-params=repeat-headers=1` so a receiver joining mid-stream syncs fast), and muxes straight to `rtp://<melchior-ip>:<port>` via `av.open(..., format="rtp")`. Start/stop: `/home/sinewave/start_d555_stream.sh [host] [port]` and `/home/sinewave/stop_d555_stream.sh` (defaults: melchior `192.168.8.175:5000`). Log: `/home/sinewave/d555_stream.log`.
- **Receiver — melchior:** `magi_detect.py` itself needed **no code changes** to accept the stream — `--input "udp://:5000"` on the existing CLI is sufficient. Start/stop helpers added: `~/magi/melchior/start_live_detect.sh [port]` and `~/magi/melchior/stop_live_detect.sh`. Log: `/home/sinewave/magi_detect_live.log` (this session's live run currently logs to `/home/sinewave/magi_detect_prod.log` instead since it was started ad hoc before the wrapper scripts existed — future runs via the script use the `_live.log` path).
- **One real code change was needed in `magi_detect.py`:** headless runs (no `DISPLAY` env var — true for any plain SSH session) were silently stalling with **zero frames ever reaching `app_callback`**, no error printed. Root cause: hailo_apps's detection pipeline always builds a `DISPLAY_PIPELINE` branch defaulting to `GST_VIDEO_SINK="autovideosink"` (hardcoded in `core/common/defines.py`); with no display, `autovideosink` tries `xvimagesink` (fails instantly), then `glimagesink` (fails to init GBM/DRM — `Could not get DRM resources: Operation not supported`), and the stalled sink stalls the whole pipeline even though the source side is flowing fine. There's no `--no-display` flag wired into `GStreamerDetectionApp`'s actual parser (`--no-display` exists in `parser.py`'s help text/comments but isn't registered for this app). Fix, added to the top of `~/magi/melchior/magi_detect.py`: monkeypatch `hailo_apps.python.core.gstreamer.gstreamer_app.GST_VIDEO_SINK = "fakesink"` at import time, **only when `os.environ.get("DISPLAY")` is falsy** — so it auto-detects headless vs. has-a-real-monitor and doesn't touch any shared hailo_apps files. Worth porting to balthazar's `magi_detect.py` too if/when that node is ever run over plain SSH without a display attached (it currently isn't hit because the bundled sample-video run apparently doesn't stall the same way — untested whether it's latent there too).
- **A second, nastier gotcha that ate most of the debugging time:** GStreamer's `udpsrc` sets `SO_REUSEADDR`, so if an old test process (e.g. a `gst-launch-1.0` smoke-test) is left bound to the same UDP port and never gets killed, **new processes can bind the same port successfully with no error, but silently receive zero packets** — the kernel keeps delivering to the older socket. Compounding it: hailo_apps calls `setproctitle()`, so every `magi_detect.py`/`gst-launch-1.0` run shows up in `ps`/`pgrep -f` as `"Hailo Detection App"` (or similar), **not** by its original script name — so `pkill -f magi_detect.py` silently matches nothing while the real process keeps squatting on the device/port. Diagnosis path that worked: `sudo ss -u -a -n -p | grep <port>` to see every socket actually bound to the port (revealed two owners), and `sudo fuser -v /dev/hailo0` to find whatever process holds the Hailo device. The `stop_live_detect.sh` helper above kills by `fuser /dev/hailo0`, not by process/script name, specifically to avoid this trap.
- **Verified end-to-end 2026-09-15 ~10:14 UTC:** with the D555 physically on audire-videre's desk and the bridge running, `magi_detect_prod.log` on melchior showed real-time `published chair (0.3x)` / `published person (0.3x)` lines with continuously varying confidences (not a fixed/repeating set, as a looping sample clip would produce), and `ssh repositorium 'sudo journalctl -u magi-worker --since "2 minutes ago"'` showed matching `persisted <msg-id> from melchior (detection)` lines within ~1 second of each publish — full D555 → audire-videre (RTP/H264) → melchior (Hailo inference) → Redis → Postgres path confirmed live.

(2) No packet-loss handling beyond what `h264parse`/`avdec_h264` tolerate natively — fine for a LAN prototype, not production-hardened. **Systemd promotion (2026-09-15) — both D555-bridge processes now real services, survive reboot/crash.** Followed `magi-worker`'s convention (`Type=simple`, `Restart=on-failure`, `RestartSec=5`) with one deliberate deviation on audire-videre explained below. The old `nohup`/`setsid` background launches were stopped via their existing `stop_*.sh` scripts (which already handled the `setproctitle()`/stale-UDP-socket gotchas noted above) before the systemd units were started, so there was no double-run/port-squatting overlap.

- **`magi-d555-stream.service` on audire-videre** — the D555 RTP/H264 sender (`magi_stream_d555.py`). Deviation from `magi-worker`'s pattern: this had to be a **user-level unit** (`~/.config/systemd/user/magi-d555-stream.service`, not `/etc/systemd/system/`), because — as already documented above — audire-videre's `sinewave` user has **no passwordless sudo** (unlike melchior/balthazar/repositorium), so `sudo systemctl`/writing to `/etc/systemd/system` isn't scriptable here. Worked around with the standard systemd mechanism for exactly this case: `loginctl enable-linger sinewave` (this itself did *not* require sudo — polkit allows a user to enable their own linger) so `user@1000.service` — and everything in it — starts at boot and keeps running with no interactive login, just like a system service. Manage with the `--user` flag: `systemctl --user status/restart/stop magi-d555-stream.service`, `journalctl --user -u magi-d555-stream -f`. Enabled via `systemctl --user enable` (symlinked into `default.target.wants`). No env vars needed — confirmed `/usr/bin/python3 -c "import pyrealsense2, av, numpy"` resolves the `--user --break-system-packages` pip installs fine under systemd's default PATH, so `ExecStart=/usr/bin/python3 -u /home/sinewave/magi_stream_d555.py --host 192.168.8.175 --port 5000` needed no wrapper script.
- **`magi-live-detect.service` on melchior** — the live Hailo detection publisher (`magi_detect.py`, includes the headless-`fakesink` monkeypatch described above). melchior *does* have passwordless sudo, so this is a normal system unit at `/etc/systemd/system/magi-live-detect.service`, `WantedBy=multi-user.target`, `User=sinewave`. Since systemd doesn't source shell profiles and `setup_env.sh` needs to be sourced (it sets `PYTHONPATH`, activates `venv_hailo_apps` by prepending its `bin/` to `PATH`, and sets several `HAILO_*`/`TAPPAS_*`/`RESOURCES_*` env vars — confirmed by diffing `env` before/after sourcing rather than guessing), `ExecStart` is a `bash -c` one-liner that replicates `start_live_detect.sh`'s own cd/source/cd sequence and ends in `exec` so the python3 process inherits the shell's PID (critical — without `exec`, systemd would track the bash wrapper as the main PID and lose clean restart/stop semantics): `ExecStart=/bin/bash -c 'cd /home/sinewave/hailo-apps && source setup_env.sh && cd /home/sinewave/magi/melchior && exec python3 -u magi_detect.py --input "udp://:5000"'`. Manage with `sudo systemctl status/restart/stop magi-live-detect`, `sudo journalctl -u magi-live-detect -f`. Confirmed `Main PID` shows as `(Hailo Detection)` (the `setproctitle()` rename) rather than `(bash)`, proving the `exec` handoff worked.
