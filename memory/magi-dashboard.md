## Where it runs

Two small components, split by where each has the most direct access to what it needs:

- **Main dashboard app — `audire-videre`** (`/home/sinewave/magi_dashboard/app.py`, Flask, port **8090**). Hosted here because this box already has passwordless SSH configured to melchior/balthazar/repositorium/edgerunner (needed for node health + detection-service control) and physically hosts the D555 camera (needed for the live preview, zero network hop). Serves the frontend (`static/index.html`) and a small JSON API.
- **Data API — `repositorium`** (`~/magi/dashboard/data_api.py`, Flask, port **8801**, systemd unit `magi-dashboard-data.service`, enabled). Hosted here because it's the only box with local (`127.0.0.1`) Postgres/Redis access under the current `pg_hba.conf` (which only allows melchior/balthazar/localhost — deliberately **not** widened to include audire-videre, to avoid touching Postgres's access control for this). Reads `~/.config/magi/worker.env` for credentials (same file `magi_worker.py` already uses) and exposes read-only aggregate JSON only — no raw DB access, no credentials, no write endpoints. The main dashboard app calls this over plain HTTP on the LAN.

Why not host it all on repositorium: SSH from repositorium out to melchior/balthazar/edgerunner isn't set up (repositorium currently only has an `authorized_keys` for *inbound* SSH, no outbound keys/config to the other nodes), and this environment's permission system blocks adding new SSH keys/authorized_keys as an "Unauthorized Persistence" action — so audire-videre's already-existing SSH trust was the right foundation to build node-health/control on instead of creating new standing access.

## Start / stop / restart

**Main app (audire-videre)** — plain background process (nohup), *not* systemd, because audire-videre's `sinewave` user has no passwordless sudo (confirmed earlier in [[magi-cluster-status]]'s D555-bridge section) so `sudo systemctl`/`/etc/systemd/system` isn't scriptable here, and this box also has no working user-lingering systemd setup verified for this app (unlike `magi-d555-stream.service`, which a concurrent session did set up as a user unit for the *streamer* — see below). Promoting the dashboard itself to a user unit the same way would be a reasonable next step but wasn't done this session (budget).
```
/home/sinewave/magi_dashboard/start_dashboard.sh   # kills any old copy by exact path, starts fresh
/home/sinewave/magi_dashboard/stop_dashboard.sh
```
Log: `/home/sinewave/magi_dashboard.log`. **Gotcha already hit and fixed once:** the start script must invoke `app.py` by absolute path — a `cd ... && python3 app.py` launch shows up in `ps` as just `python3 app.py` with no distinguishing path, so a path-based `pkill -f` silently matches nothing on "restart," leaving a stale pre-restart process serving forever while the new one dies on the port conflict. Both scripts now use the absolute path consistently; don't regress this.

**Data API (repositorium)** — real systemd unit:
```
sudo systemctl status|restart|stop magi-dashboard-data   # on repositorium
sudo journalctl -u magi-dashboard-data -f
```

**Camera streamer (audire-videre)** — `magi-d555-stream.service`, a **user** systemd unit (`systemctl --user ...`), set up by a concurrent session this same day — see the "Systemd promotion" section in [[magi-cluster-status]] for why it's user-level (no passwordless sudo on this box) and how `loginctl enable-linger` makes it survive without an interactive login. The dashboard's MJPEG preview code lives *inside* `magi_stream_d555.py` (same process, same capture loop — see below), so this is the same service; don't run a second copy manually with `nohup`, it'll fight the systemd-managed one for the RealSense device handle and the preview port. Manage with `systemctl --user status|restart|stop magi-d555-stream`.

**melchior's detect service** — also promoted to systemd (`magi-live-detect`, system-level, melchior has passwordless sudo) by that same concurrent session. The dashboard's start/stop/restart buttons for melchior now call `sudo systemctl start|stop|restart magi-live-detect` over SSH (**not** the old raw `start_live_detect.sh`/`stop_live_detect.sh` scripts) — calling the raw scripts directly would just get fought/undone by systemd's `Restart=on-failure`. Verified working: a restart via the dashboard button brought detection back within ~10s with a fresh PID.

**balthazar's detect service** — **no systemd unit yet** (out of scope for the concurrent systemd-promotion session). Dashboard control still uses the original raw scripts, added this session: `~/magi/balthazar/start_detect.sh` / `stop_detect.sh`, mirroring melchior's pre-systemd pattern (kill by `fuser /dev/hailo0`, not by process/script name — `hailo_apps` calls `setproctitle()` so a plain `pkill -f magi_detect.py` silently matches nothing). If balthazar ever gets promoted to systemd too, **update `NODES["balthazar"]` in `app.py` to add a `restart_cmd` using `systemctl`**, same as melchior, or the dashboard's control buttons will start fighting it.

## What it shows

- **Cluster node health** — melchior/balthazar/repositorium/edgerunner: reachable y/n, uptime, load average, SSH round-trip latency. Polled live via SSH each request (no caching), ~5s refresh in the UI.
- **HAT interaction** — per Hailo node: whether the detect process is genuinely running (via `fuser /dev/hailo0`, **not** `pgrep -f "Hailo Detection App"` — see the bug note below, that approach is broken), whether the Hailo device itself is visible (`hailortcli scan`), and Start/Restart/Stop buttons. No chip-temperature readout — `hailortcli measure-power`/temp commands need exclusive device access and fail while detection is running; skipped per the task's own "don't spend excessive effort here" guidance.
- **Camera** — live MJPEG preview at `/api/camera/mjpeg` (also a single-frame `/api/camera/snapshot.jpg`), proxied through the main app from a small HTTP server added directly inside `magi_stream_d555.py` (threaded, shares the same capture loop/frame buffer as the RTP-to-melchior path — no second RealSense pipeline opened, the device doesn't like concurrent opens). ~12fps preview cap, independent of the 30fps capture/encode rate to melchior.
- **Data flow** (Redis `magi:detections` stream + Postgres `events`) — stream length, consumer-group lag (`XINFO GROUPS`), events in the last 60s/5m, rate/min, a bar chart of detection counts by class (last 10 min), and a live table of the most recent ~15 detections (device/class/confidence/time-ago). This is served by repositorium's data API and polled every 3s.
- **Pi network topology** — static description (from [[magi-cluster-status]]'s network-topology section) of the two physical LAN segments and how data flows between nodes; not live-probed, just documentation rendered in the UI.
- **Failover status (added 2026-09-16, see [[magi-failover]])** — per-node/per-role (vision/language) heartbeat health (healthy/stale/stopped + age), whether each node is currently in "failover mode," and Force start/Force stop override buttons per role. Read from repositorium's Redis `magi:heartbeat:*` keys via a new `data_api.py` endpoint, polled every 5s.

Frontend follows the `dataviz` skill's method: dark-mode-selected theme using its validated reference palette (status colors for node up/down and detect running/stopped, single-hue blue for the class-count bar ranking, direct labels instead of a legend since each bar/card is already named).

## Local LLM chat — "offload to melchior" (added 2026-09-16)

A third component: **`magi-llm-api`** on melchior (`~/magi/melchior/magi_llm_api.py`, Flask, port **8802**, systemd unit `magi-llm-api.service`, enabled). Wraps melchior's Hailo-10H local LLM (Qwen2.5-Coder-1.5B-Instruct via `hailo_platform.genai.LLM`) — see [[magi-local-llm-feasibility]] Session 4/5 for the full story of how this was proven and built. `POST /chat {"prompt": "..."}` → `{"response": "...", "elapsed_s": ...}`, synchronous, requests serialized (single non-blocking lock — a second concurrent request gets `429 busy` immediately, no queueing). Same systemd pattern as `magi-live-detect` (`source ~/hailo-apps/setup_env.sh` in ExecStart, `User=sinewave`, `Restart=on-failure`).

The main dashboard app proxies to it at `POST /api/llm/chat` (90s timeout, relays melchior's status/body as-is including `429`), and the frontend (`static/index.html`) has a "Local LLM — offload to melchior" panel: textarea, Send button, response box with a thinking/spinner state, elapsed-time readout. General Q&A answers in a few seconds; code-generation requests can take ~40-60s — this is expected and shown in the UI copy, not a bug.

**Balthazar now has `magi_llm_api.py` too (added 2026-09-16, see [[magi-failover]])** — but installed as **failover-only**, `magi-llm-api.service` present but disabled/inactive by default, never the dashboard's default chat target. Testing found it cannot coexist with balthazar's actual day-to-day language service, `hailo-ollama`/Open WebUI (crashes hailo-ollama outright under concurrent load) — see [[magi-failover]] for the full finding. The dashboard's chat panel above still always talks to melchior; balthazar's copy only gets started automatically by the new failover watchdog (or a manual override) if melchior goes down.

**Verified end-to-end 2026-09-16**: real (non-mocked) responses confirmed both via direct curl to melchior:8802 and through the full dashboard proxy path at `/api/llm/chat`, for both a general-knowledge question and a code-generation request. Confirmed `magi-live-detect.service` stayed active and detections kept landing in repositorium's Postgres throughout, including during a 39.6s code-gen request — no crash, some throughput sharing expected per Hailo's own docs.

**Update (2026-09-16, same day, follow-up session) — tool-calling + conversation history added.** Full details/verification evidence in [[magi-local-llm-feasibility]]'s Session 6; summary here for the dashboard-specific pieces:

- **Tool calling**: `magi_llm_api.py` on melchior now embeds math + weather tool schemas (from `agent_tools_example`, reused verbatim) into the system prompt and actually executes them when the model emits a `<tool_call>`. Verified through the dashboard: "what's 23 times 17?" → real tool execution → `391`; weather-in-Chicago → real live Open-Meteo data. Hardware tools (LED/servo/elevator) are not imported into this process at all, so there's no path to real GPIO from the dashboard chat. The chat response meta line now shows `tool used: <name>` when applicable, and the `/chat` JSON has `tool_used`/`tool_result` fields.
- **Conversation history**: new session concept — the browser generates a `session_id` (stored in `localStorage`, key `magi_llm_session_id`) and sends it with every `/api/llm/chat` call. History is stored in a new Postgres table (`llm_conversations`) via a new service, **`magi-conversation-api`** on **repositorium** (systemd, port **8803**, `~/magi/dashboard/conversation_api.py`) — melchior has no direct Postgres access itself, so it calls this service over plain HTTP to load/save turns. A **"New conversation" button** next to Send clears the current session's history (`DELETE /api/llm/session/<id>` on the dashboard → melchior → repositorium) and rotates to a fresh session id. Verified end-to-end: told it a name + topic in turn 1, asked "what's my name and what am I working on?" in turn 2 (same session), got the correct answer back — proves history round-tripped through Postgres and was actually used, not just a stateless coincidence.
- **A dashboard-specific bug fixed this session**: `app.py`'s `/api/llm/chat` proxy originally forwarded only `{"prompt": ...}` to melchior and silently dropped `session_id` — history looked broken end-to-end even though melchior's side worked fine when hit directly. Fixed by forwarding `session_id` through the proxy. Worth remembering if this proxy is touched again: fields added to melchior's API don't reach the dashboard (or vice versa) automatically, they're two separate files.
- **Safety note**: a transient live-active under-voltage/throttle bit (`0x50005`, not just the historical `0x50000`) was observed once during this session's testing, self-cleared within seconds. Testing was stopped at that point per the standing power-safety protocol; the plain one-shot Q&A/code-gen path (this section's original feature) was *not* re-verified after this session's code changes as a result — recommend a fresh check once the power situation is more stable.

**Update (2026-09-17) — real scrollable chat-thread UI, replacing the single-latest-response box.** Conversation history was already persisted server-side (the section above), but the frontend only ever showed the newest response, wiping the previous one each time — so a user watching a slow reply land (e.g. Gil's real 41s weather query, confirmed genuinely successful via `journalctl` on balthazar) had no way to see their earlier turn actually got answered, and re-sending follow-ups just looked like "nothing changed." Fixed by building a real thread:

- **New backend proxy**: `GET /api/llm/history/<session_id>` in `app.py`, forwarding to repositorium's `magi-conversation-api` (`GET http://192.168.8.184:8803/conversations/<session_id>?limit=N`, verified live and reachable — not guessed). Returns `{"session_id", "turns": [{"role","content","created_at"}, ...]}` oldest-first, passed straight through. New constant `CONVERSATION_API = "http://192.168.8.184:8803"` (repositorium; same host as `DATA_API`, different port) plus a dedicated `CONVERSATION_HISTORY_TIMEOUT_S = 10`.
- **Frontend (`static/index.html`)**: the old single `#chat-response` box is now `#chat-thread`, a flex-column scrollable container (`max-height: 480px` desktop / `360px` at the existing `<=600px` breakpoint, `overflow-y: auto`) holding one `.chat-msg` bubble per turn — user messages right-aligned/blue (`var(--series-1)`), assistant messages left-aligned/dark (`var(--surface-1)`, monospace for code), each with a small uppercase role label and, for assistant replies, a per-message meta subtext line (timestamp, elapsed seconds, `served_by`, `tool_used`, failover note) — replacing the old single shared `#chat-meta` bottom line for that purpose (`#chat-meta` is now purely the static "how this works" description, never mutated by JS).
- **On page load**, `loadChatHistory()` fetches the current session's history and renders it oldest-to-newest, auto-scrolled to bottom. **On send**, `submitChat()` is optimistic: the user's bubble appends immediately, then a `thinking` bubble appends (its own thread entry, not a replacement) with a live `"Still working... (Ns elapsed)"` ticker (`setInterval`, 1s) so a long wait reads as in-progress rather than stalled; that same bubble is mutated in place into the final assistant/error bubble when the response lands, rather than the thread being cleared and redrawn.
- **No client-side fetch timeout** — verified by reading the code, not assumed: no `AbortController` anywhere in `index.html`. `fetch()` genuinely waits up to `app.py`'s existing 90s upstream proxy timeout.
- **"New conversation"** (`newConversation()`) unchanged in mechanism (still `DELETE /api/llm/session/<id>` + rotates `localStorage`'s `magi_llm_session_id`) but now also resets `#chat-thread` to an empty-state message instead of clearing a single response box.
- Removed the old "fresh response" flash-animation/sequence-number indicator (`.chat-response-flag`, `chat-flash` keyframes, `chatSeq` display) — redundant now that every response is visibly its own new bubble appended to a growing thread; `chatSeq` variable kept (now just an internal counter, unused for display).
- **Verified end-to-end** (2026-09-17, via a fresh real conversation through the actual proxy chain — direct Postgres access was correctly refused by this environment's credential-materialization guard, so verification used the app's own endpoints, not raw `psql`): a 2-turn real conversation's history round-tripped correctly through `GET /api/llm/history/<id>` in order; `DELETE /api/llm/session/<id>` genuinely emptied Postgres for that session (confirmed via the history endpoint returning `turns: []` after); rendered correctly in headless Chromium (driven directly over the DevTools Protocol, no Node/Playwright driver available on this box) at 375×812, 768×1024, 1920×1080, and 3440×1440 with zero console errors; a real code-generation request (`Write a Python function that returns the nth Fibonacci number using memoization.`, 15.4s, through the actual browser UI/click path) showed the live elapsed ticker update mid-request and then correctly replaced in place with the formatted code response, thread never cleared, user's message still visible above it throughout.

## Voice response — "Read responses aloud" toggle (added 2026-09-17)

Text-to-speech output for the LLM chat panel, scoped deliberately to TTS-only (the assistant speaking its replies) — speech-to-text input (dictating a prompt in) was explicitly out of scope this round; see "Natural follow-up" below.

**New component: `magi-tts`, running on audire-videre itself, not melchior/balthazar.** A small standalone Flask service (`/home/sinewave/magi_dashboard/tts/magi_tts.py`, its own venv at `tts/venv_tts/`, port **8804**, `systemctl --user` unit `magi-tts.service`, enabled — same pattern as `magi-d555-stream.service`: audire-videre has no passwordless sudo, so it's a **user** unit, not system-level, kept alive across reboots via `loginctl enable-linger` which was already set for this user). `POST /tts {"text": "..."}` → raw `audio/wav` bytes. `GET /health`.

**Where it runs and why — investigated, not assumed:** read `hailo-apps`'s own `gen_ai_utils/voice_processing/text_to_speech.py` and `README.md` directly (on melchior, where the hailo-apps repo lives) before deciding placement. Confirmed Piper TTS (`piper-tts` PyPI package) is pure Python + ONNX Runtime — `text_to_speech.py` never imports `hailo_platform` or touches the Hailo device at all; the Hailo-specific pieces of the voice stack are only Whisper (STT) and the LLM itself, not Piper. This means TTS has zero NPU/Hailo dependency, so it was deliberately placed on **audire-videre** (16 cores, 31GB RAM, 770GB disk, not power/thermal-constrained the way the Pi5s are) instead of melchior/balthazar — avoids any risk to `magi-live-detect`/`magi-llm-api` on those boxes and needed no `hailo-apps` install at all, just `pip install piper-tts flask` into a fresh venv (`python3 -m venv`, since audire-videre's system Python is externally-managed/PEP-668 and refuses bare `pip install`).

**Model**: `en_US-amy-low` (~61MB ONNX + json config), downloaded via `python3 -m piper.download_voices en_US-amy-low` into `tts/piper_models/`. Real measured performance on audire-videre's CPU: model load ~1s at service startup (kept loaded, not per-request), synthesis of a full sentence ~0.2-0.3s — far faster than the "seconds not tens of seconds" bar in the task brief, and well under the LLM's own multi-second-to-a-minute response times it follows.

**Decoupled from `magi_llm_api.py` by design** — per the task's explicit architecture guidance (another agent was concurrently touching that file on melchior/balthazar for an unrelated tool-migration). `magi_tts.py` never talks to melchior/balthazar at all; the dashboard frontend calls `/api/tts` as a second, independent step *after* a chat response has already rendered via the existing `/api/llm/chat` flow. `magi_llm_api.py` was not touched on either node.

**Dashboard wiring:**
- New proxy `POST /api/tts` in `app.py` (`TTS_API = "http://127.0.0.1:8804"`, 20s timeout) — forwards `{"text": ...}` to the local `magi-tts` service and streams the `audio/wav` response straight through.
- New checkbox in the chat panel's button row (`static/index.html`): `🔊 Read responses aloud`, styled as a plain accent-colored checkbox (`--series-1` accent, matching every other accent use in the dashboard) rather than a custom switch component — invoked the `dataviz` skill first per this environment's standing rule, but since this is a form control (not a chart), the skill's applicable guidance was just "stay within the existing token/color conventions," which this follows.
- **State persisted in `localStorage`** (`magi_tts_enabled`, `"1"`/unset), same pattern as the existing `magi_llm_session_id` — survives a page reload. Off by default (no autoplay surprise on first visit).
- On a successful (non-error, non-429) chat response, if the toggle is on, `speakText(data.response)` fires: `POST /api/tts` with the rendered response text, then plays the returned WAV blob via `new Audio(objectURL)` / `.play()`. This never blocks or delays the chat UI — a TTS failure (service down, network hiccup) is swallowed with a `console.warn`, not surfaced as a chat error, since the text answer already rendered successfully regardless.
- **Long/code-heavy responses**: `magi_tts.py` strips fenced ```` ``` ```` code blocks before synthesis (replaced with a short spoken "Code block omitted from audio" note) and unwraps inline `` `code` `` backticks — reading raw Python line-by-line aloud isn't useful. Also caps synthesis at 2000 characters server-side (`MAX_TTS_CHARS`) so a very long response doesn't turn into a multi-minute clip.

**Verified end-to-end (2026-09-17), real audio not mocked:**
- Direct `magi-tts:8804/tts` and through the full dashboard proxy `/api/llm/chat` → `/api/tts` chain, both real (non-mocked) requests: valid `RIFF/WAVE, 16-bit mono 16000Hz` files produced each time (confirmed via `file` and Python's `wave` module — e.g. a real "Paris is the capital of France." response synthesized to a 2.19s, 70188-byte WAV).
- Code-block stripping verified: a test string containing a fenced ` ```python ` block synthesized successfully with the code portion replaced by the spoken omission note.
- Headless Chromium (`--headless=new --dump-dom`) load of the dashboard showed the toggle rendered correctly in the DOM with no stderr/console errors.
- `magi-tts.service` confirmed healthy via `systemctl --user status` (~200MB RSS, single voice model kept loaded) and `magi-d555-stream.service` (camera streamer, same host) confirmed still running untouched throughout — no resource contention observed on a 16-core/31GB box for a task this light.

**Natural follow-up, not built this round**: speech-to-text input (dictating a prompt into `#chat-input` via the mic instead of typing) — Gil didn't explicitly ask for it this time, and the task scoped this round to voice *response* only. The Hailo Whisper STT path exists in the same `hailo-apps` voice stack (`gen_ai_utils/voice_processing/speech_to_text.py`) but is NPU-bound (imports `hailo_platform`, needs a `VDevice`), so unlike Piper it likely *would* need to live on melchior/balthazar — a materially different placement decision than this round's, worth its own investigation rather than assuming it follows the same "run it on audire-videre" pattern.

## `find_nearby` chat tool + one-time location capture (added 2026-09-18)

"Find me directions to the nearest Best Buy" now works as a single chat request — see
[[magi-osrm-routing]]'s "`find_nearby` LLM tool" section for the full build/verification writeup
(Overpass API integration, token-budget fix, location-handling design). Dashboard-specific summary:

- **New frontend helper `getOneShotLocation()`** in `static/index.html` — calls
  `navigator.geolocation.getCurrentPosition()` **once** (4s timeout, resolves `null` on any

## Live Navigation panel — opt-in GPS + live re-routing (added 2026-09-17)

A new, separate UI surface (not the chat thread, not LLM-orchestrated) for turn-by-turn-ish live navigation using the browser's own GPS. Deliberately **not** wired into the LLM tool-calling system — the existing `directions` chat tool stays a one-shot "give me a route" Q&A; this is a dedicated panel that tracks live position and re-routes on a timer.

**Backend — new `/nav/route` endpoint on repositorium's `tools_api.py`** (same `magi-tools-api.service`/port 8804 process the `directions` tool already lives in, chosen because that's where the self-hosted OSRM instance already is):
- `run_nav_route()` / `compute_route(lat, lon, dest_lat, dest_lon)` — `compute_route()` is the single seam function for all route+ETA computation, documented in its own docstring as **the traffic-data extension point**: it currently always calls this box's self-hosted OSRM (`192.168.8.184:5000`), which has zero live traffic data (static road-network/speed-limit routing only, per [[magi-osrm-routing]]). When Gil sets up a commercial traffic-aware routing API account (his own separate future step — deliberately not built speculatively here, no provider/API shape guessed at without real credentials), the intended swap point is this one function's implementation (or a provider-config branch inside it) — callers (the `/nav/route` endpoint, and the frontend) only depend on its return shape (`ok`, `distance_mi`/`distance_km`, `duration_min`/`duration_str`, `eta_utc`, `next_instruction`, `geometry`, `provider`), not on OSRM specifically.
- `POST /nav/route` body: `{"lat", "lon", "destination"}` (first call — geocodes via the same rate-limited Nominatim helper the `directions` tool uses) or `{"lat", "lon", "dest_lat", "dest_lon"}` (every call after — client caches the geocoded destination itself so a live-tracking session never re-geocodes the same place on a timer, respecting Nominatim's 1 req/sec policy).
- **Re-routing design**: deliberately stateless / no server-side polyline-distance heuristic. Every poll computes a fresh route from wherever the client says it currently is to the destination — which *is* re-routing on deviation, by construction, without extra threshold logic to get wrong. Geometry is decimated to ≤100 points before being returned (client doesn't need every OSRM vertex; no map widget renders it, v1 is text-only per the task's scope).
- **Privacy**: `/nav/route` logs at `debug`, not `info` (explicit inline comment explaining why — polled every ~15-30s during active navigation, logging every lat/lon at `info` would build an incidental location history in the journal). No Postgres/Redis/disk write of position anywhere, at any level.

**Dashboard proxy** — `POST /api/nav/route` in `app.py` (new `TOOLS_API = "http://192.168.8.184:8804"` constant, `NAV_ROUTE_TIMEOUT_S = 10`), a stateless passthrough to repositorium's endpoint above.

**Frontend — `static/index.html`**, a new "Live Navigation (opt-in GPS)" card, separate from the chat thread, placed between the Open WebUI card and the Camera section:
- Destination text input, "Start navigation" / "Stop navigation" buttons, a status line, and a result card (distance remaining, ETA/duration text explicitly noting "no live traffic data", next-turn instruction, last-updated timestamp).
- **Opt-in only**: `navigator.geolocation.watchPosition()` is called *only* inside `startNavigation()`, i.e. only after the user clicks the button — never on page load, never automatically. The browser's own permission prompt gates it further.
- **Throttling**: `navMaybeRoute()` only actually calls `/api/nav/route` when either ≥20s have passed since the last call (`NAV_POLL_INTERVAL_MS`) or the position has moved ≥60m since the last routed position (`NAV_MOVE_THRESHOLD_M`, via a plain Haversine helper) — so a `watchPosition` callback firing frequently doesn't hammer OSRM every second, per the task's explicit constraint.
- **Stop / cleanup**: `stopNavigation()` clears the geolocation watch (`clearWatch`) and the polling interval, and resets all in-memory nav state — nothing is persisted anywhere (not localStorage, not any backend store). A `beforeunload` listener calls the same cleanup if the tab closes/navigates away mid-session.
- Styling followed the `dataviz` skill's standing-rule invocation for this session; since this is form controls/text tiles (not a chart), the applicable guidance was staying within existing tokens — reused `.card`/`.chat-row`/`.chat-input`/`.chat-submit`/`.tile-label`/`.tile-value`/`.node-stat` classes and the existing color tokens rather than introducing new ones.

**Verified 2026-09-17** (no real GPS device available in this environment, so verified by calling `/nav/route` directly with simulated lat/lon pairs approximating movement along the same Willis-Tower→O'Hare route used in prior OSRM testing, plus one far-off-route point):

- A 4th call from a position far off the route (Chicago's South Side, same destination) returned a genuinely different route (31.51mi/1hr9min, first turn "East 80th Street" vs. the original "West Adams Street") — confirms real re-routing on deviation, not a cached/stale result.
- Error paths checked directly: non-numeric `lat`/`lon` and a missing `destination`/`dest_lat`+`dest_lon` both return clean `{"ok": false, "error": "..."}` rather than a 500.
- Full path verified too: `curl POST http://127.0.0.1:8090/api/nav/route` (the dashboard's own proxy, not just repositorium directly) returned the same correct result.

## Known limitations

1. **Tailnet access not yet live** — see Access section above; blocked on edgerunner being reachable.
2. **Dashboard app itself isn't systemd-managed** — a crash or audire-videre reboot won't auto-restart it; needs a manual `start_dashboard.sh` run (or promote it to a user unit like the streamer, later).
3. **No auth** — fine for LAN/tailnet-only, would need one before any wider exposure.
4. **balthazar detect control still script-based, not systemd, for the main HAT panel** — the original detect-control buttons (`NODES["balthazar"]` in `app.py`) still use the raw `start_detect.sh`/`stop_detect.sh` scripts, unchanged. Note there IS now a separate `magi-live-detect.service` systemd unit on balthazar (added 2026-09-16 for [[magi-failover]]), but it's `disabled`/inactive by default and managed only by the failover watchdog/manual-override path, not by these HAT panel buttons — the two control paths coexist but are intentionally separate; don't assume promoting one reconciles the other. **Caution**: clicking the old HAT panel's "Start" button for balthazar while the failover system has separately started `magi-live-detect.service` (or vice versa) would race two processes for `/dev/hailo0` — not expected in normal operation (failover mode is rare/short-lived) but worth knowing if detect ever behaves oddly on balthazar during/near a failover window.
5. Node health / hailo-device-present checks add a few hundred ms of SSH round-trip per node per poll (~5s interval) — fine at this scale, wouldn't scale to many more nodes without batching.
6. A real bug was hit and fixed during build: an early version checked Hailo detect status with `pgrep -f "Hailo Detection App"` run over SSH — this **self-matches the wrapping SSH command's own argv** (which contains that same literal string), so it always reported "running" regardless of truth. Fixed to use `fuser /dev/hailo0` instead (same technique the existing stop scripts already used, for a related but distinct reason). If extending node-health checks later, be wary of `pgrep -f`/`ps grep` patterns run remotely for the same self-match trap.
