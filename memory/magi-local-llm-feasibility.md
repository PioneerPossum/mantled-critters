Research pass (2026-09-15) answering the open question from [[magi-offline-claude-proposal]]: can melchior/balthazar's Hailo-10H NPUs run general LLM inference for Gil's "local physical agent" dashboard idea? **Short answer: yes, plausibly — Hailo ships an official GenAI stack for Hailo-10H specifically, including a tool-calling agent example that's very close to what Gil described. But none of it is installed or tested yet on either node — everything below is from reading source/docs, not from running a model.** Both melchior and balthazar are Hailo-10H (confirmed via `hailortcli fw-control identify` — `Device Architecture: HAILO10H`, firmware 5.1.1), so they clear the hardware gate Hailo puts on GenAI features.

## What's actually there (gen_ai_apps, both nodes, verified identical tree)

`~/hailo-apps/hailo_apps/python/gen_ai_apps/` is a full GenAI example suite, not just the voice-troubleshoot stub the proposal doc had found:

- **`agent_tools_example/`** — an interactive CLI chat agent with automatic tool discovery (`tool_*.py` modules), function calling, token-based context management (clears at 80% capacity), and **context caching to disk** so re-running the same tool loads instantly instead of re-priming the system prompt. Ships working tools: math, weather (Open-Meteo, no API key), RGB LED, servo, elevator — real hardware or Flask-simulator mode. This is the closest existing thing to the "Claude-Code-like agent with tool use and persistent context" Gil asked for.
- **`simple_llm_chat/`** — minimal one-shot text completion example (`hailo_platform.genai.LLM`), good for a smoke test.
- **`vlm_chat/`**, **`simple_vlm_chat/`** — vision-language model chat (image Q&A), not needed for this use case but notable that it exists.
- **`voice_assistant/`**, **`simple_whisper_chat/`**, **`gen_ai_utils/voice_processing/`** — STT (Whisper)/TTS (Piper) pipeline; out of scope for a text dashboard but available if voice input is ever wanted.
- **`hailo_ollama/`** — Hailo's own **Ollama-API-compatible REST server** (`hailo-ollama`, C++ on HailoRT, listens on `:8000`) plus an Open WebUI Docker integration guide. This is a separate, more "batteries included" path to the same models.
- **`gen_ai_utils/llm_utils/`** — the shared plumbing behind all of the above: context management, message formatting, streaming with tag filtering, tool discovery/execution/parsing, terminal UI. Reusable building blocks if a custom dashboard backend is written instead of reusing `agent_tools_example` as-is.

**Not installed on either node right now.** `pip list` on melchior shows only `hailort`/`hailo-tappas-core-python-binding` — no `piper-tts`, no `sounddevice`, and `hailo_platform.genai` doesn't import. `/usr/local/hailo/resources` (1.6GB) contains only the existing YOLO/CLIP vision models, nothing GenAI. `hailo-download-resources` isn't even on `PATH` in the current venv. Getting GenAI working requires, per the docs: `pip install -e ".[gen-ai]"` from the hailo-apps repo root, **plus** downloading and `apt install`-ing a separate `hailo_gen_ai_model_zoo_<ver>_<arch>.deb` package from `hailo.ai/developer-zone` (gated behind a Hailo developer account — supported versions 5.1.1/5.2.0/5.3.0; melchior's HailoRT is 5.1.1, so compatible), then pulling an actual model on first run.

## Model scale — real evidence, not guesswork

The `hailo_ollama` README's worked example pulls `qwen2.5-instruct:1.5b`, and `agent_tools_example`'s own README links to a "Qwen 2.5 Coder (1.5B) Tool Calling" reference notebook. That's a solid, concrete signal (not inference from general Hailo marketing) that the Hailo-10H GenAI stack targets **~1.5B–3B parameter, heavily quantized instruction/coder models** — small, fast, edge-appropriate models, not anything GPT-4-class. Expect competent short Q&A, boilerplate code, and simple tool-calling; not deep multi-step reasoning or large-context work.

No hard numbers were obtainable this session for tokens/sec, context length limit, or on-chip model-weight memory budget — `hailortcli fw-control identify --extended` reports firmware/SoC/board info but no GenAI-specific capacity figures, and nothing could be benchmarked without actually installing the stack and downloading a model (a real install+download+benchmark pass is the natural next step once Gil decides this is worth pursuing).

## Concurrency with the existing YOLO detection pipeline — good news, with one real limit

`~/hailo-apps/doc/user_guide/running_parallel.md` states explicitly:
- **Vision + GenAI concurrently: supported.** Both use `SHARED_VDEVICE_GROUP_ID` to share the device; the doc's own guidance is "total throughput may be lower than running a single application" — a resource-sharing tradeoff, not a hard conflict.
- **GenAI + GenAI concurrently: explicitly *not* supported** ("they use the same service and cannot run simultaneously"). Each Hailo-10H can run at most one LLM chat session at a time. This actually aligns naturally with Gil's "two physical agents" framing — one LLM agent per Pi, each also still running its live YOLO detection — rather than being a real constraint on the proposed design.

## Fallback option: CPU-based llama.cpp (in case the Hailo GenAI path disappoints)

Neither `llama-cli`/`llama.cpp` nor `ollama` is installed on either node currently (checked `which` and `dpkg -l`, nothing found). Pi5's 4x Cortex-A76 @ 2.4GHz is a well-known quantity in the wider llama.cpp/Pi5 community — realistic expectations are roughly single-digit tokens/sec on a 3B Q4 model, slower on anything bigger, entirely CPU-bound. This is a legitimate fallback but doesn't use the Hailo hardware Gil specifically bought for this, and would compete for the same 4 CPU cores that the GStreamer/Python glue around the Hailo detection pipeline also uses (the NPU inference itself is offloaded, but frame decode/muxing/Python callback overhead is real CPU work already happening on these boxes).

## Storage backend sanity check

repositorium's existing Postgres 15 + pgvector 0.8.0 (`magi_memory` DB, per [[magi-cluster-status]]) is a reasonable fit for LLM conversation history/embeddings — no real concerns. One small schema note: the existing `events.embedding` column is `VECTOR(512)`, sized specifically for CLIP ViT-B/32 image embeddings. Text-embedding models for conversation memory typically use different dimensions (384/768/1024 are common), so LLM conversation embeddings would likely want either a new table or a differently-sized nullable vector column — a minor migration, not a blocker, and doesn't need resolving before a build decision.

## Architecture options, ranked

**Option A (recommended primary path) — Native Hailo-10H GenAI stack, built on `agent_tools_example`.**
Install the gen-ai extras + model zoo `.deb` + a ~1.5–3B Qwen2.5-class model on each node; adapt `agent_tools_example`'s tool-discovery/context-caching framework as the dashboard's backend agent loop (swap its CLI I/O for HTTP endpoints the dashboard calls). Pros: uses the NPU Gil bought specifically for this; closest existing code to the "tool use, persistent context" agent shape Gil wants; Vision+GenAI concurrency is officially supported so detection doesn't have to stop. Cons: completely unvalidated on this hardware so far — install, model download, and first real prompt are all still ahead; quality ceiling is a small quantized model, not deep-reasoning-capable; per-node GenAI sessions are serialized (one chat at a time per Pi, which is fine for the "2 agents" framing but rules out e.g. multiple simultaneous dashboard users hitting the same node).

**Option B (secondary/implementation-detail variant) — Hailo-Ollama REST API as the backend, skip building a custom agent loop.**
Run `hailo-ollama` (Hailo's packaged Ollama-compatible server) on each node and have the dashboard backend talk to its REST API directly (skip deploying Open WebUI itself — that's a consumer chat UI, overkill next to Gil's own dashboard). Pros: less custom Python to write/maintain, standard Ollama-client libraries work out of the box. Cons: loses `agent_tools_example`'s context-caching and tool-discovery scaffolding — function-calling support depends on hailo-ollama's own compatibility layer and is unverified this session; adds a second long-running daemon per node.

**Option C (fallback only, not primary) — CPU-based llama.cpp, bypass the Hailo NPU for text generation entirely.**
Pros: mature ecosystem, huge model choice, no Hailo developer-zone account or `.deb` gating, well-documented Pi5 performance expectations already exist in the community. Cons: doesn't use the NPU at all (the whole point of the hardware Gil already owns for this); shares the same 4 CPU cores as the detection pipeline's non-NPU overhead; would need a hand-rolled tool-calling loop since none of Hailo's scaffolding applies. Recommend keeping this in reserve only if Option A's install/benchmark pass turns out disappointing (blocked account gating, incompatible HailoRT version, or genuinely bad tokens/sec once actually measured).

## Session 3 conclusion — hard confirmation, HailoRT 5.1.1 genuinely lacks a required API

Gil installed the OpenSSL dev packages directly. `cmake -B build -DCMAKE_BUILD_TYPE=Release` on melchior then succeeded cleanly — it found `HailoRT 5.1.1` via `find_package`, resolved OpenSSL 3.5.7, fetched oatpp/json/eventpp/minja, generated build files with no errors. `cmake --build build --config Release -j4` compiled ~95% of the tree (all of oatpp, oatpp-openssl, most of `hailo-ollama-lib`) before failing with a genuine, unambiguous compile error — not a linker/runtime issue, a source-level API mismatch:

```
src/library/generation_context/generation_context.cpp:106:27: error: no matching function for call to
  ‘hailort::genai::LLM::generate(const LLMGeneratorParams&, const vector<string>&, const vector<string>&)’
```
against the installed `/usr/include/hailo/genai/llm/llm.hpp` (from `h10-hailort` 5.1.1), which only declares:
- `generate(const vector<string>& prompt_json_strings)` — 1 arg
- `generate(const LLMGeneratorParams&, const vector<string>& prompt_json_strings)` — 2 args

No 3-argument overload taking a `tools_json_strings` vector exists in 5.1.1's headers at all. `hailo-ollama`'s source (targeting 5.4.0) calls the 3-arg tool-calling-aware overload. **This is a hard, source-level confirmation that tool-calling support was added to `LLM::generate` between HailoRT 5.1.1 and 5.4.0** — not a packaging/linking/naming issue, not something fixable by adjusting CMake flags or build config, and not something to paper over (e.g. dropping the third argument would silently disable tool-calling and isn't a faithful substitute for the real API — did not attempt this).

**Conclusion: both the prebuilt `hailo-ollama` binary (needs `libhailort.so.5.4.0` at the dynamic-link level) and building from source (needs the 5.4.0-era `LLM::generate` API surface, absent from 5.1.1's headers) independently confirm the same thing: `hailo-ollama`/the gen-ai model zoo genuinely requires HailoRT ≥5.4.0 on this hardware. There is no way to run it against 5.1.1 as installed — not via the .deb, not via source build.** The only remaining paths are (a) upgrade HailoRT on melchior to 5.4.0, accepting the real risk to the production `magi-live-detect` service that this doc has flagged as a stop-and-ask point from the start, or (b) drop Option B (hailo-ollama) and look at Option A (`agent_tools_example` + `pip install -e ".[gen-ai]"`) to see if its Python `gen-ai` extras have looser version requirements — untested, worth checking before committing to a runtime upgrade.

Throughout this entire session (installs, dry-runs, source clone/build, held-package management): `magi-live-detect.service` stayed `active`, `hailortcli --version` stayed `5.1.1`, `h10-hailort`/`hailo-h10-all`/`python3-h10-hailort` stayed held at 5.1.1 and untouched, and fresh detections from both melchior and balthazar continued landing in repositorium's Postgres via `magi-worker` throughout (confirmed via journalctl at multiple checkpoints, most recently right after the failed build). ## Session 4 (2026-09-16) — Option A actually run on melchior. IT WORKS on HailoRT 5.1.1, no upgrade needed.

**Bottom line: yes.** `agent_tools_example` runs end-to-end against the held 5.1.1 runtime — general Q&A, code generation, and genuine tool-calling (math + live weather) all confirmed working with real measured numbers, no HailoRT upgrade, no risk to `magi-live-detect`.

**Why this works where Option B failed:** `agent_tools_example` never calls the 3-arg `LLM::generate(params, prompt, tools)` overload that only exists in HailoRT ≥5.4.0 (the thing that sank both the prebuilt `hailo-ollama` binary and the from-source build in Sessions 2–3). It calls the plain `generate(prompt)`/`generate(params, prompt)` forms that **do** exist in 5.1.1, and does tool-calling entirely at the prompt layer: tool schemas get embedded as text in the system prompt (`system_prompt.py`), the model emits `<tool_call>{"name":...,"arguments":...}</tool_call>` in its text output, and `gen_ai_utils/llm_utils/tool_parsing.py` regex/JSON-parses it back out, then `tool_execution.py` actually calls the real Python function. ## Session 13 (2026-09-17) — root-cause fix for the whole "post-tool garbage response" bug class: stop generating a second time

**The bug, confirmed a third time, new shape.** Live on balthazar (default node): "what is 12 plus 15?" → `tool_used: "math"`, `tool_result: {"ok": true, "result": "12 + 15 = 27"}` (tool executed correctly) — but the user-facing `response` was a hallucinated, wrong, irrelevant tool-schema blob: `"<code>\n{\n \"type\": \"function\",\n \"name\": \"weather\",\n ...\n}\n</code>"`. Reproduced live on melchior first (per the usual melchior-first protocol) 3/3 before touching anything. This is a new shape of the same bug class Session 9 partially fixed (degenerate `<5`-char output, or a re-hallucinated `<tool_call>{...}</tool_call>` block) — it's wrapped in `<code>` tags instead, so Session 9's `parse_function_call()` re-check didn't catch it and it leaked straight to the user.

**Root-cause fix, not another narrow detector.** Every tool this project has (math, weather, directions — the third tool a concurrent Session 12/13 thread added) already returns a well-formed, natural-language-ready `tool_result["result"]` string (`"12 + 15 = 27"`, `"Current conditions in Seattle, United States: 20.0°C as of 6:45 PM. Today's forecast: high 21.4°C, low 10.8°C. Precipitation today: 0.0mm expected (0% chance)."`, `"Driving from Willis Tower... 22.0 mi (35.4 km), about 56 min. Key turns: ..."`). Sanity-checked this directly against several hours of real `magi-llm-api` journal logs on balthazar before committing to the fix — every sampled `tool_result` across math/weather/directions/failed-weather read as a complete, correct, ready-to-show answer on its own; no evidence the second `_generate()` call (the one that turns the tool result into a "natural-language reply") ever added anything of value, only risk (it's the sole source of every garbage-output shape hit across Sessions 6, 9, and now 13).

**Change (in `chat()`, both nodes' `magi_llm_api.py`, byte-identical as always):** removed the second post-tool `_generate([tool_msg], prefix="")` call entirely, for both success AND failure. `final_text` is now set unconditionally to `_tool_result_fallback_text()` (Session 9/10's existing fallback helper, already handles the success case, the generic failure case, and the special-cased weather "ask the user for a location" clarifying-question case). The no-tool plain Q&A/code-gen path (fresh-context retry-with-new-seed on `<5`-char degenerate output) is untouched — different code path, not implicated in this bug class.
